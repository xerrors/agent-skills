## 核心契约

只改进最近修改代码的清晰度、一致性和可维护性，严格保留功能、输出和可观察行为。清晰优先于短小，直接优先于聪明。

这是 quality-only 工作流，不主动寻找或顺手修复原实现中的 correctness bug。分析角色发现行为缺陷时返回 `REVIEW_REQUIRED`，主智能体把它留给单独的 `review`，不得借“简化”改变需求或修复语义。

使用固定管线：

```text
Gather recent diff
→ Reuse / Simplification / Efficiency / Altitude 并行分析
→ wait barrier + dedupe
→ single writer edits
→ behavior / quality 并行验证
→ 收敛后运行最终检查
```

## Phase 0：锁定范围与行为

1. 用一句话写出最小验收标准和必须保持的行为。若存在多个会改变编辑方向的合理解释，暂停歧义候选并请求确认。
2. 只纳入用户显式 scope，或本次会话当前任务刚修改的文件与行块，以及这些行块直接产生的未使用 import、变量、函数和分支。
3. 不把进入任务前已存在的 dirty worktree、相邻旧代码或历史技术债自动纳入。无法可靠区分时跳过歧义文件。
4. 记录仓库根目录、`git status`、原始 diff、diff hash、适用项目规则、需求与可用基线测试结果。
5. 阅读理解候选所需的直接调用点、现有工具和测试，但不得借此扩大可编辑范围。

把原始 diff 作为行为基线。四个分析 Agent 都接收同一 scope、需求、diff 获取方式和规则路径，不接收其他 Agent 的候选或预期答案。

## Phase 1：四角度并行分析

并行启动四个固定的只读 cleanup Agent；并发槽位不足时分最少批次运行，但四个角度都必须完成。

### 1. Reuse

搜索仓库已有工具、组件、服务和稳定模式，识别本次改动重复实现的解析、转换、验证、错误处理或 UI 能力。只有现有能力真正匹配当前语义、且替换不会扩大行为或 scope 时才建议复用。

### 2. Simplification

寻找不必要的分支、状态、嵌套、重复条件、重复转换、无意义临时值、只复述代码的注释和可拉直的主流程。优先明确命名、早返回、集中相关逻辑和 Stepdown Rule，不追求最少行数。

### 3. Efficiency

寻找本次改动引入的重复计算、重复 I/O、不必要遍历、分配、序列化、请求或资源占用。只有优化同时保持时序、错误、副作用、复杂度约束和可读性时才作为 simplify 候选；性能担忧没有具体成本时跳过。

### 4. Altitude

判断抽象层级是否合适：识别单次使用的抽象、薄 wrapper、纯参数转发 helper、过早通用框架、未来配置和把主流程拆碎的调用链；同时保护真正形成稳定边界、隔离副作用或被多处清晰复用的抽象。

每个 Agent 返回：

```text
path + line
summary
concrete_cost: 当前造成的重复、认知或资源成本
proposed_change
behavior_preservation_argument
scope_fit
verdict: CANDIDATE | SKIP | REVIEW_REQUIRED
skip_reason（适用时）
```

风格偏好、无法证明的“更优雅”、行为变化、范围外问题和误报必须返回 `SKIP` 并说明原因。correctness bug 返回 `REVIEW_REQUIRED`，不能伪装为 cleanup 候选。

## Phase 2：Barrier 与去重

等待四个 Agent 全部完成，再按 path、重叠位置和根因去重。保留来自不同角度的互补证据，不让先返回的意见影响后续 Agent。

主智能体只采纳同时满足以下条件的候选：

- 位于已授权 scope，且解决由最近修改引入或暴露的具体成本。
- 能说明所有相关行为为何保持不变。
- 符合适用项目规则。
- 修改后确实更易读、调试或维护，而不只是行数更少。
- 不需要产品、架构或兼容性选择。

更简单但需要扩大改动面的方案进入“保留项与取舍”，说明收益、扩大范围和风险；不得直接实施。误报、无具体收益和行为无法证明的候选都跳过并记录原因。

## Phase 3：单写者编辑

只允许主智能体或一个明确指定的 writer 修改工作树。不得把不同候选分给并行写入者。

对每个拟采纳候选完整执行 Claude Code 的六步简化循环：

1. 确认候选属于最近修改的代码。
2. 指出要消除的具体复杂度、重复、不一致或资源浪费。
3. 应用适用项目规则和现有代码惯例。
4. 逐项证明功能、输出和可观察行为保持不变。
5. 编辑后重新阅读主流程，确认结果确实更简单、更清楚，而非更紧凑。
6. 只把影响理解的重要变化留给最终总结。

按依赖顺序实施最小修改。每组关联修改后立即检查 diff 和 scope；删除仅由本次简化产生的孤儿代码，不触碰用户原有变更或无关格式。

常用手段：复用真正匹配的现有能力、合并相同分支、拉直主路径、使用早返回、把紧密职责放回一起、把具名值放在最小合理作用域、删除无价值间接层，以及让文件从高层意图逐步下降到实现细节。

## Xerrors 简化顺序

1. 锁定验收标准与行为契约，不默默补需求。
2. 审查本次改动加入但验收标准未要求的配置、兼容层、扩展点和推测性灵活性；只有能证明它未接入、不可达、纯内部且无可观察行为，或用户明确授权移除时才删除。
3. 删除重复实现和已被等价机制完整承接的冗余 fallback。
4. 让相关职责集中、主流程线性完整，优先直接表达、早返回和 Stepdown Rule。
5. 只保留服务于明确复用、隔离副作用或实质降低认知负担的 helper 与抽象。
6. 命名表达意图，注释解释原因、约束或不变量，不复述语法行为。
7. 只清理由本次改动产生的孤儿代码。
8. 测试中可合并重复 setup 和低价值用例，但不得弱化真实行为、关键字段或副作用断言。

## 必须保持的行为

不得改变：

- 对外 API、参数、返回值、错误类型和错误时机。
- 数据写入、事件、日志、网络调用和其他副作用的条件、次数与顺序。
- 权限、安全、事务、并发、缓存、重试、恢复和兼容语义。
- 用户可见文案、交互、可访问性和平台行为，除非用户明确纳入目标。
- 关键时间或空间复杂度、资源上限和性能契约。
- 测试所表达的真实业务契约。

Fallback、`try/catch`、重试和保底分支可能本身就是错误、恢复或兼容契约。只有能证明它冗余或不可达，或已有等价机制完整承接其条件、时机、错误和副作用时才能删除；否则保留并列为未实施候选。

## 避免过度简化

- 不以减少行数为目标，不制造密集一行式、嵌套三元或隐晦技巧。
- 不把多个职责塞进巨型函数、组件或类。
- 不删除真正隔离副作用、形成稳定边界或被多处清晰复用的抽象。
- 不为“统一”创建新框架，也不把局部细节提升成全局配置。
- 不把相关逻辑拆成更多细碎 helper，迫使读者跨文件或跨函数追踪主流程。
- 不弱化测试断言、扩大 skip、增加不必要 mock，或修改测试来掩盖行为差异。
- 不顺手改写无关命名、注释、格式和相邻旧代码。

## Phase 4：并行验证与收敛

编辑后对最终 diff 并行启动两个只读 Verifier：

1. **Behavior-preservation Verifier**：对照原始 diff、行为清单和测试，检查返回值、错误时机、副作用次数与顺序、事务、并发、兼容性和性能是否变化。
2. **Simplification-quality Verifier**：确认认知负担和具体成本确实下降，没有产生巨型函数、密集技巧、新重复、无关修改、抽象层级倒退或项目规范回归。

主智能体处理验证意见后，只要做了任何纠正编辑，就重新检查 diff，并再次并行运行两个 Verifier。最多执行两轮纠正；仍不能收敛时撤销未收敛候选的编辑，并对最终版本完成一次行为与质量检查。只有最终版本已经被两者检查且没有未解决问题时才结束验证循环。

若无法消除某项行为差异，撤销仅属于该候选的编辑并报告原因；绝不回滚用户原有修改。若 Verifier 发现原始改动中的 correctness bug，不在 simplify 中修复，把它列为 `review required`。

## 最终验证

按风险由窄到宽执行：

1. 检查最终 diff、scope、未使用 import、重复分支、孤儿代码和意外格式化。
2. 运行最小相关测试，优先验证真实业务字段和副作用。
3. 风险需要时扩大回归测试，再运行项目要求的静态检查、构建和 `git diff --check`。
4. 对比基线与最终结果；基线原本失败时区分既有失败和新失败。

不得把未运行写成通过，也不要仅凭测试通过声称所有行为完全不变。无法运行时列出具体原因和未验证范围。

## 输出

```markdown
## 已简化

- `path/to/file.py`：<删除、合并或复用了什么，以及主流程为何更直接。>

## 验证

- `<实际命令>`：通过 / 失败（原因）/ 未运行（原因）

## 保留项与取舍

- <因行为风险、范围扩大或需要决策而未实施的候选；没有则写“无”。>

## Review required

- <只列分析中发现但未修复的 correctness 风险；没有则省略本节。>
```

只总结有理解价值的变化。不要声称“功能完全不变”，除非自动化与人工证据足以支持；准确报告已执行验证和剩余不确定性。

## 降级执行

宿主不支持子智能体时，单线程依次完成 Reuse、Simplification、Efficiency 和 Altitude 四个角度，再由同一智能体分两遍执行行为与质量验证。最终明确标注“降级执行：未完成并行子智能体编排”，不得省略任何角度或声称完成并行流程。

Claude Code 的独立 simplifier 可配置为在编码后主动运行；本 skill 的完整多智能体分支为了避免扩大普通编码任务，只在用户显式调用或明确要求时启动。
